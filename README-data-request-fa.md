# README درخواست داده MarginLift

این فایل را بعد از جلسه با تیم Data، CRM و Finance میلی‌گلد یا دیجی‌پی استفاده کنید. هدف، گرفتن کمترین داده‌ی لازم برای یک Diagnostic معتبر و آماده‌کردن مسیر پایلوت است.

MarginLift قرار نیست CRM یا ابزار ارسال پیام باشد. کار آن این است که با داده‌ی تاریخی و سپس یک آزمایش کنترل‌شده مشخص کند کدام مشتری واقعاً به اقدام نیاز دارد، کدام مشتری بدون مشوق هم خرید می‌کند، و کدام سیاست در نهایت سود مشارکتی بیشتری ایجاد می‌کند.

## اصل مهم

در مرحله اول فقط داده‌ی ناشناس و حداقل لازم را بگیرید. برای تحلیل تاریخی، شناسه‌ی مشتری باید پایدار باشد. برای ادعای اثر افزایشی، علاوه بر داده‌ی تاریخی، assignment، گروه کنترل، اقدام واقعی و outcome مالی لازم است.

داده‌ی نمونه یا فایل کوچک برای بررسی فنی قابل قبول است؛ اما برای Live Holdout و ادعای «سود تأییدشده» کافی نیست.

## بعد از جلسه چه چیزی باید تحویل بگیریم؟

| اولویت | خروجی | حداقل پیشنهادی |
| --- | --- | --- |
| P0 | Data Dictionary | نام ستون، نوع داده، تعریف، مالک، واحد پول و timezone |
| P0 | نمونه ناشناس | حداقل ۱۰۰ ردیف با ساختار واقعی، بدون PII |
| P0 | فایل تراکنش تاریخی | ترجیحاً ۱۲ ماه؛ حداقل شروع Diagnostic برابر ۶ ماه |
| P0 | تعریف کسب‌وکار | تعریف خرید موفق، ریزش، خرید دوم، بازپرداخت و سود |
| P1 | فایل کمپین و اقدام | سیاست، گروه، زمان تخصیص، زمان ارسال و هزینه واقعی |
| P1 | منبع مالی | margin/commission، هزینه مشوق، هزینه کانال و refund |
| P2 | خروجی Live Holdout | Assignment قفل‌شده و یک Outcome برای هر مشتری |

## مسیر A: فایل تاریخی مشترک

این فایل برای Data Readiness، baseline خرید مجدد، تحلیل چرخه خرید و تشخیص اولیه ریسک استفاده می‌شود. هر ردیف باید یک تراکنش یا رویداد مالی واقعی باشد.

| ستون | الزام | فرمت و قاعده |
| --- | --- | --- |
| `customer_id_hash` | اجباری | شناسه‌ی ناشناس، پایدار و یکسان در همه فایل‌ها |
| `transaction_id` | اجباری | شناسه یکتا؛ برای هر تراکنش فقط یک ردیف |
| `purchased_at` | اجباری | ISO-8601، مثلاً `2025-02-03T10:15:00+03:30` |
| `transaction_status` | اجباری | یکی از `completed`, `failed`, `refunded`, `cancelled` |
| `product_id` | اجباری | شناسه محصول/SKU بدون اطلاعات شخصی |
| `product_category` | پیشنهادی | دسته محصول برای تحلیل cohort و رفتار |
| `paid_amount` | اجباری | عدد صحیح، بدون جداکننده؛ واحد باید اعلام شود |
| `net_revenue` | ترجیحی | درآمد خالص یا commission واقعی پس از کسر برگشت |
| `contribution_margin` | بسیار مهم | سود مشارکتی همان تراکنش پس از هزینه متغیر |
| `discount_amount` | ترجیحی | تخفیف مستقیم استفاده‌شده؛ صفر واقعی با مقدار خالی فرق دارد |
| `cashback_amount` | ترجیحی | کش‌بک یا اعتبار اعطاشده |
| `incentive_cost` | ترجیحی | هزینه واقعی مشوق برای کسب‌وکار |
| `channel_cost` | ترجیحی | هزینه واقعی push، SMS، in-app یا کانال دیگر |
| `campaign_id` | پیشنهادی | شناسه کمپین، در صورت انتساب |
| `channel` | پیشنهادی | `app`, `web`, `push`, `sms`, `call` یا مقدار توافق‌شده |

برای فایل اول، اگر `contribution_margin` در دسترس نیست، `net_revenue` ارسال شود و صریحاً نوشته شود که نتیجه فقط بر مبنای درآمد است و اعتماد مالی پایین‌تر خواهد بود.

## مسیر B: مخصوص میلی‌گلد

### هدف پایلوت

- افزایش احتمال خرید دوم.
- جلوگیری از توقف پس‌انداز و خریدهای تکراری.
- تشخیص اینکه کدام مشتری به یادآوری، پیشنهاد یا مشوق نیاز دارد.

### ستون‌های اضافه‌ی ارزشمند

| ستون | چرا لازم است؟ |
| --- | --- |
| `saving_plan_id` یا شناسه طرح ناشناس | تشخیص رفتار تکرارشونده در هر طرح |
| `gold_product_type` | تفکیک خرید طلا، پس‌انداز یا محصول مرتبط |
| `installment_number` | تشخیص توقف در میانه مسیر پس‌انداز |
| `balance_or_saved_value` | اندازه‌گیری ارزش در معرض ریزش، بدون ارسال حساب شخصی |
| `purchase_interval_days` | مقایسه cadence واقعی کاربران |
| `price_at_purchase` | کنترل اثر تغییر قیمت طلا و فصل |
| `redemption_or_withdrawal_status` | تفکیک توقف خرید از برداشت/تسویه |

### تعریف‌هایی که باید از میلی‌گلد بگیریم

1. خرید دوم از چه فاصله‌ای بعد از خرید اول «موفق» محسوب می‌شود؟
2. توقف پس‌انداز چند روز یا چند قسط بعد «ریزش کانال» محسوب می‌شود؟
3. margin یا commission واقعی هر نوع محصول چیست؟
4. آیا مشوق شامل تخفیف، کارمزد کمتر، کش‌بک یا اعتبار خرید است؟
5. خرید و برداشت چگونه از یکدیگر جدا می‌شوند؟

## مسیر C: مخصوص دیجی‌پی

### هدف پایلوت

- افزایش استفاده مجدد از BNPL.
- افزایش خرید مجدد کاربران دارای اعتبار.
- کاهش ریزش و افزایش engagement.
- جلوگیری از هدررفت هزینه مارکتینگ با ارسال اقدام فقط برای افراد نیازمند.

### ستون‌های اضافه‌ی ارزشمند

| ستون | چرا لازم است؟ |
| --- | --- |
| `service_type` | تفکیک BNPL، خرید اعتباری، شارژ، بسته و سرویس دیگر |
| `credit_eligibility_status` | جداکردن نبود تقاضا از نبود اعتبار |
| `credit_limit_band` | استفاده از بازه به‌جای مقدار حساس اعتبار |
| `credit_used_band` | اندازه‌گیری استفاده بدون ثبت مقدار دقیق در خروجی |
| `repayment_status` | تشخیص ریسک بازپرداخت از ریزش رفتاری |
| `days_past_due` | کنترل اثر تأخیر پرداخت در تحلیل retention |
| `merchant_category` | تحلیل خرید مجدد در دسته‌های مختلف |
| `marketing_cost` | تطبیق هزینه واقعی کمپین با سود افزایشی |
| `app_engagement_event` | مانند ورود، مشاهده پیشنهاد یا شروع checkout، در صورت مجازبودن |

### تعریف‌هایی که باید از دیجی‌پی بگیریم

1. «استفاده مجدد از BNPL» دقیقاً خرید جدید است یا فعال‌سازی اعتبار هم محسوب می‌شود؟
2. کاربر دارای اعتبار اما بدون خرید چگونه تعریف می‌شود؟
3. ریزش در افق ۳۰، ۹۰ و ۱۸۰ روز چه تعریفی دارد؟
4. درآمد، commission دیجی‌پی است یا GMV؟
5. هزینه اعتبار، یارانه، cashback و کمپین در کدام منبع مالی ثبت می‌شود؟
6. کدام رویداد engagement مجوز استفاده در مدل را دارد و کدام رویداد نباید وارد شود؟

## مسیر D: فایل کمپین و سیاست فعلی CRM

برای مقایسه‌ی منصفانه با وضعیت فعلی، فقط تاریخچه‌ی خرید کافی نیست. باید بدانیم چه سیاستی روی چه کسی اجرا شده است.

| ستون | الزام | توضیح |
| --- | --- | --- |
| `campaign_id` | اجباری | شناسه کمپین |
| `customer_id_hash` | اجباری | دقیقاً همان شناسه فایل تاریخی |
| `assigned_policy` | اجباری برای پایلوت | مثل `current_crm_policy` یا `marginlift_policy` |
| `assigned_group` | اجباری برای آزمون | `control` یا `treatment`، پیش از ارسال اقدام |
| `assigned_at` | اجباری | زمان تخصیص، نه زمان ارسال |
| `delivered_at` | ترجیحی | زمان تحویل پیام/پیشنهاد |
| `exposed_at` | ترجیحی | زمان مشاهده یا exposure واقعی |
| `action_type` | اجباری | `no_action`, `message_no_discount`, `targeted_discount` |
| `incentive_cost` | اجباری برای تحلیل سود | هزینه واقعی مشوق استفاده‌شده |
| `channel_cost` | ترجیحی | هزینه واقعی اجرای کانال |
| `policy_version` | اجباری | نسخه سیاستی که تصمیم را ساخته است |
| `overlap_flag` | اجباری برای پایلوت | آیا کمپین دیگری در پنجره فعال بوده است؟ |

اگر سیاست فعلی CRM قابل ثبت و بازتولید نباشد، MarginLift فقط می‌تواند با `persistent_no_action` مقایسه شود و نباید ادعا کند از CRM بهتر است.

## مسیر E: فایل Live Holdout و Outcome

### Assignment

Assignment را MarginLift پس از قفل قرارداد تولید می‌کند. مشتری نباید ستون‌های آن را تغییر دهد.

ستون‌های اصلی خروجی:

```csv
experiment_id,assignment_id,customer_id_hash,assigned_policy,assigned_at,outcome_closes_at,assignment_registry_hash,analysis_plan_version
```

این فایل باید در رجیستری مشتری با `assignment_registry_hash` و `outcome_closes_at` نگه‌داری شود.

### Outcome سی‌روزه

پس از بسته‌شدن پنجره ۳۰روزه، برای هر Assignment دقیقاً یک ردیف برگردانید؛ حتی اگر خریدی رخ نداده باشد.

```csv
customer_id_hash,assigned_policy,actual_action,assigned_at,delivered_at,exposed_at,outcome_at,repurchased,net_revenue,contribution_margin,incentive_cost,channel_cost,refund_amount,opt_out,complaint,contaminated
```

قواعد Outcome:

- نبود خرید با `repurchased=false` و اعداد مالی صفر ثبت شود؛ حذف ردیف مجاز نیست.
- زمان‌ها باید با timezone مشخص و داخل پنجره ۳۰روزه باشند.
- `assigned_policy` باید با Assignment قفل‌شده یکسان باشد.
- `contaminated` نباید خالی بماند؛ آلودگی کمپین هم‌زمان باید ممیزی شود.
- اعداد مالی باید از منبع Finance قابل تطبیق باشند.
- تحلیل اصلی ITT است؛ کاربر با Delivery ناموفق از گروه تخصیص‌یافته حذف نمی‌شود.

## استاندارد حریم خصوصی و امنیت

ارسال این موارد ممنوع است:

- نام و نام خانوادگی، شماره موبایل، ایمیل و آدرس.
- کد ملی، شماره کارت، شماره حساب و اطلاعات پرداخت خام.
- IP، device ID، advertising ID و متن پیام شخصی.
- شناسه خام CRM یا هر کلیدی که به‌تنهایی فرد را شناسایی کند.

استاندارد شناسه:

- شناسه در سمت مشتری با HMAC-SHA256 و secret متعلق به همان مشتری ساخته شود؛ secret برای MarginLift ارسال نشود.
- همان شناسه برای فایل تاریخی، کمپین، Assignment و Outcome استفاده شود.
- hash ساده‌ی شماره موبایل بدون secret کافی نیست.

## استاندارد فرمت و کیفیت

- فایل ترجیحاً UTF-8 CSV باشد؛ جداکننده comma و header یکتا داشته باشد.
- اعداد بدون comma و بدون متن واحد پول باشند؛ واحد `toman` یا `rial` در Data Dictionary نوشته شود.
- همه تاریخ‌ها ISO-8601 باشند و timezone اعلام شود؛ پیشنهاد پایه `Asia/Tehran` یا UTC است.
- مقدار خالی با صفر یکی نیست. صفر فقط وقتی ثبت شود که واقعاً صفر باشد.
- وضعیت‌های موفق، ناموفق، برگشت و لغو از هم جدا باشند.
- `transaction_id` یکتا باشد و duplicate پنهان نشود.
- ردیف‌ها به‌ترتیب زمانی مرتب شوند یا روش مرتب‌سازی در Data Dictionary اعلام شود.
- حداقل ۹۵٪ ردیف‌ها باید شناسه، زمان و وضعیت معتبر داشته باشند؛ failureهای واقعی حذف نشوند.
- refund، chargeback و cancellation باید قابل ردیابی باشند.
- ستون‌های مالی در صورت نبود مقدار نباید با مقدار تخمینی پر شوند.
- داده‌ی بعد از تاریخ امتیازدهی نباید وارد feature تاریخی شود؛ این موضوع در MarginLift کنترل می‌شود.

## گیت پذیرش MarginLift

| وضعیت | شرط |
| --- | --- |
| `needs_data_fix` | PII، شناسه ناپایدار، تاریخ نامعتبر، duplicate جدی یا ستون‌های اصلی ناقص |
| `diagnostic_only` | فایل خواندنی است، اما پوشش زمانی، تکرار خرید یا نمونه کافی نیست |
| `ready` | فایل برای ساخت baseline و برنامه‌ریزی پایلوت آماده است |
| `live_ready` | Metric Contract قفل، دو Shadow سالم، نمونه کافی و سیاست اجراپذیر است |

`ready` به‌تنهایی مجوز تخفیف یا ادعای اثر افزایشی نیست. `live_ready` نیز تا پایان Outcome و تطبیق Finance فقط به معنی مجوز شروع آزمایش است.

## حداقل سؤال‌های جلسه

در پایان جلسه باید پاسخ مکتوب این سؤال‌ها را داشته باشید:

1. KPI اصلی برای مدیر چیست: خرید مجدد، retention، سود مشارکتی یا ترکیبی؟
2. مالک CRM، Data، Finance و Experiment چه کسانی هستند؟
3. سیاست فعلی CRM دقیقاً چیست و آیا قابل بازتولید است؟
4. آیا گروه کنترل یا holdout قابل ثبت وجود دارد؟
5. درآمد و margin از کدام جدول یا mart مالی می‌آید؟
6. پنجره outcome مورد توافق ۳۰ روز است؟ پیگیری ۹۰ و ۱۸۰ روزه چگونه انجام می‌شود؟
7. فایل را از چه مسیر امنی تحویل می‌دهند؟
8. معیار توقف کمپین و سقف قابل‌قبول opt-out و شکایت چیست؟

## بعد از دریافت فایل چه اتفاقی می‌افتد؟

1. MarginLift فایل را Preview می‌کند و hash، mapping، حریم خصوصی و کیفیت را گزارش می‌دهد.
2. در صورت خطا، فایل ذخیره نمی‌شود و لیست اصلاحات برمی‌گردد.
3. پس از Import، baseline خرید مجدد و Data Readiness ساخته می‌شود.
4. با Finance و CRM، Metric Contract و thresholdها نسخه‌گذاری و قفل می‌شوند.
5. دو Shadow Run بدون تماس با مشتری اجرا می‌شود.
6. پس از تأیید گیت‌ها، Assignment قفل‌شده تولید می‌شود.
7. بعد از ۳۰ روز، Outcome وارد، integrity بررسی و با Finance تطبیق داده می‌شود.
8. خروجی نهایی یکی از این سه تصمیم است: `Scale`، `Review` یا `Stop`.

## خروجی‌ای که مشتری دریافت می‌کند

- گزارش آمادگی داده و فهرست دقیق خطاها.
- baseline چرخه خرید و cohortهای قابل تفسیر.
- صف تصمیم با سطح شواهد و بدون ادعای causal زودهنگام.
- Assignment قابل اجرای CRM، بدون PII.
- گزارش مدیریتی یک‌صفحه‌ای با سود افزایشی، guardrail، ریسک و اقدام بعدی.
- Decision Receipt قابل حسابرسی برای هر تصمیم.

## نکته پایانی برای تیم مشتری

فایل کامل شش‌ماهه را فقط از مسیر امن و مورد تأیید سازمان تحویل دهید. برای جلسه اول، ۱۰۰ ردیف ناشناس به‌همراه Data Dictionary کافی است تا مشخص شود آیا قرارداد داده، تعریف KPI و مسیر پایلوت قابل اجرا هستند یا نه.
