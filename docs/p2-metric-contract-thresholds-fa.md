# کاربرگ Metric Contract نسخه P2

این کاربرگ قبل از قفل‌کردن قرارداد باید با مالک CRM، مالک داده و نماینده Finance تکمیل شود. اعداد زیر جای حدس محصول را نمی‌گیرند؛ از baseline و محدودیت اقتصادی همان مشتری استخراج می‌شوند.

## ترتیب تکمیل

1. معیار اصلی را قفل کنید: `Incremental Contribution Profit 30d per Assigned Eligible Customer`.
2. واحد پول را صریحاً روی تومان یا ریال بگذارید و منبع تبدیل را ثبت کنید.
3. انحراف معیار سود مشارکتی هر مشتری را از یک cohort تاریخی هم‌تعریف محاسبه کنید.
4. حداقل اثر مالی قابل تشخیص را با Finance انتخاب کنید؛ این عدد کوچک‌ترین اثر اقتصادی معنادار برای تصمیم است، نه بهترین سناریو.
5. حداقل نمونه هر سیاست را با فرمول دو میانگین مستقل تعیین کنید:

   `n_per_policy = ceil(2 × SD² × (z(1−α/2) + z(power))² / MDE²)`

   تنظیم پیش‌فرض سیستم `α=0.05` و `power=0.80` است. اگر `minimumSamplePerPolicy` از عدد محاسبه‌شده کمتر باشد، قفل قرارداد مجاز نیست.

## Thresholdهای تصمیم

| فیلد | روش تعیین | مالک تأیید |
| --- | --- | --- |
| کف درآمد افزایشی هر مشتری | حداقل صفر، مگر Finance کف بالاتری برای هدف اقتصادی تعیین کند | Finance |
| سقف افزایش هزینه مشوق | بر اساس حداکثر هزینه مجاز به‌ازای مشتری و margin واقعی | Finance + CRM |
| سقف افزایش opt-out | baseline همان cohort به‌علاوه بیشینه افزایش قابل‌قبول تجربه مشتری | CRM |
| سقف افزایش شکایت | baseline ثبت‌شده به‌علاوه آستانه مصوب ریسک/Compliance | CRM + Compliance |

در `thresholdBasisFa` باید منبع baseline، تاریخ استخراج، پنجره زمانی، نسخه دفتر مالی و دلیل انتخاب هر threshold نوشته شود. جمله‌هایی مانند «به‌صورت تقریبی» یا «برای تست» مبنای قفل قرارداد نیستند.

## شرایط قفل

- داده مشتری واقعی و غیرنمونه باشد.
- وضعیت Readiness برابر `ready` و dataset hash معتبر باشد.
- سیاست فعلی CRM ثبت‌پذیر و قابل‌بازتولید باشد.
- دو Shadow Run متوالی از یک نسخه داده و policy سالم باشد.
- سه تأیید CRM، Data و Finance در Ledger ثبت شده باشد.
- پس از قفل، تغییر threshold فقط با ساخت نسخه جدید انجام شود.

## نتیجه فعلی این workspace

در snapshot فعلی MarginLift، آخرین تحلیل `diagnostic_only`، با ۱۲ ردیف و بدون dataset hash معتبر است. بنابراین قرارداد قابل قفل و Assignment واقعی قابل صدور نیست. بعد از ورود داده مشتری و تکمیل این کاربرگ، مسیر مجاز چنین است:

`نسخه قرارداد → ذخیره → تأیید CRM/Data/Finance → قفل → دو Shadow سالم → ثبت آزمایش → دریافت Assignment`
