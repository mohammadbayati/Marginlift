# Model Governance و Monitoring

## هدف

این لایه مانع می‌شود یک بهبود آفلاین یا هم‌بستگی تاریخی به‌اشتباه مجوز تغییر مدل یا افزایش بودجه تلقی شود. چهار خروجی مستقل نگهداری می‌شوند: بک‌تست، calibration، drift و نتیجه واقعی پایلوت.

## Backtest

- تقسیم train/test بر اساس hash پایدار `customer_id` انجام می‌شود تا یک مشتری بین foldها جابه‌جا نشود.
- برچسب outcome مانند `churned` وارد featureهای امتیازدهی نمی‌شود تا target leakage رخ ندهد.
- Champion فعلی با همان منطق شفاف ریسک و سود محصول ارزیابی می‌شود.
- Challenger از shrinkage برای محافظت در برابر اثرهای اغراق‌شده گروه‌های کوچک استفاده می‌کند.
- transformed outcome فقط یک diagnostic آفلاین است؛ در داده مشاهده‌ای ادعای causal تولید نمی‌کند.
- کمتر از ۴۰ ردیف یا کمتر از ۱۰ مشاهده در هر بازوی کنترل و اقدام، وضعیت `insufficient_sample` می‌گیرد.

## Promotion Gate

ارتقای Challenger فقط با تحقق هم‌زمان این شروط قابل بررسی است:

- حداقل ۲۰۰ مشتری و ۵۰ مشتری در هر بازو
- برتری calibration و policy value نسبت به Champion
- حداقل یک پایلوت تصادفی decision-grade
- تکرار نتیجه در دو پنجره مستقل
- تأیید انسانی محصول و داده

در نسخه فعلی `autoPromotion=false` و `autoScale=false` است.

## Drift

- متغیرهای عددی با PSI پایش می‌شوند.
- متغیرهای دسته‌ای با Jensen-Shannon divergence پایش می‌شوند.
- افت completeness ستون‌های قراردادی نیز به‌عنوان drift ثبت می‌شود.
- آستانه هشدار `0.10` و آستانه بحرانی `0.25` است.
- نخستین import فقط baseline می‌سازد؛ مقایسه از import دوم آغاز می‌شود.
- پروفایل ذخیره‌شده شامل خلاصه توزیع است و داده خام یا `customer_id` در API عمومی نمایش داده نمی‌شود.
- نام سگمنت و کانال پیش از ذخیره پروفایل hash می‌شوند و cardinality پروفایل سقف دارد.

## Decision Ledger

ورود داده، ثبت آزمایش و ارزیابی outcome در یک زنجیره SHA-256 ثبت می‌شوند. هر رکورد hash رکورد قبلی همان سازمان را نگه می‌دارد. تغییر رکوردهای قدیمی، بررسی یکپارچگی زنجیره را ناموفق می‌کند.
