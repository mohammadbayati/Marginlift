# اسکریپت جلسه qualification

هدف جلسه اول فروش نیست؛ هدف این است که بفهمیم آیا درد «هدررفت مشوق» واقعی، قابل‌اندازه‌گیری و دارای مالک داخلی است یا نه.

## ساختار ۲۵ دقیقه‌ای

| دقیقه | بخش | هدف |
| --- | --- | --- |
| ۰ تا ۳ | مقدمه کوتاه | توضیح اینکه قرار نیست داده خام کاربر بگیریم |
| ۳ تا ۱۰ | کشف کمپین‌ها | فهمیدن نوع مشوق، تکرار و مالکیت |
| ۱۰ تا ۱۷ | کشف داده و کنترل‌گروه | فهمیدن امکان تحلیل uplift |
| ۱۷ تا ۲۲ | ارزش اقتصادی | تخمین اندازه مسئله |
| ۲۲ تا ۲۵ | next step | توافق روی پایلوت یا توقف محترمانه |

## متن شروع جلسه

«هدف من این نیست که در جلسه اول دمو طولانی بدهم. می‌خواهم بفهمم آیا مسئله‌ای که MarginLift حل می‌کند برای شما واقعی است یا نه: اینکه چه بخشی از تخفیف/اعتبار به کاربرانی داده می‌شود که بدون آن هم خرید می‌کردند. اگر مسئله واقعی بود، یک پایلوت کوچک با داده aggregate پیشنهاد می‌دهم؛ اگر نبود، همان‌جا متوقفش می‌کنیم.»

## سؤال‌های اصلی

۱. در ماه چند کمپین فعال‌سازی، بازگشت یا تخفیف دارید؟

۲. مشوق‌ها بیشتر به چه شکل هستند: کد تخفیف، اعتبار، ارسال رایگان، cashback، پوش، پیامک یا ترکیب؟

۳. الان تصمیم می‌گیرید چه کسی چقدر مشوق بگیرد؟

۴. آیا برای کمپین‌ها کنترل‌گروه دارید؟

۵. اگر کنترل‌گروه دارید، گزارش فعلی بیشتر conversion را نشان می‌دهد یا سود افزایشی را هم حساب می‌کند؟

۶. آخرین بار چه زمانی کمپینی داشتید که فروش بالا رفت اما تیم مالی/مدیریت درباره هزینه تخفیف سؤال کرد؟

۷. اگر ۱۰٪ از بودجه مشوق بدون افت فروش کم شود، این عدد تقریبا برایتان چقدر ارزش دارد؟

۸. چه کسی تصمیم نهایی برای تغییر policy کمپین را می‌گیرد؟

۹. اجرای یک تست ۴هفته‌ای با داده aggregate از نظر امنیت/حقوقی قابل‌قبول است؟

۱۰. اگر بعد از تحلیل بفهمیم یک سگمنت باید مشوق نگیرد، آیا تیم شما اجازه اجرای آن تصمیم را دارد؟

## امتیاز qualification

| معیار | ۰ | ۳ | ۵ |
| --- | --- | --- | --- |
| درد اقتصادی | تخفیف مسئله مهمی نیست | هزینه مشوق مهم است اما عدد ندارد | بودجه مشوق و فشار سود کاملا مشخص است |
| داده | داده کمپین ندارد | داده پراکنده دارد | CSV/BI aggregate قابل‌خروجی دارد |
| کنترل‌گروه | ندارد و حاضر به تست نیست | ندارد اما برای کمپین بعدی می‌پذیرد | دارد یا آماده طراحی کنترل‌گروه است |
| مالک داخلی | نامشخص | یک تیم علاقه‌مند | مالک و تصمیم‌گیر مشخص |
| سرعت اجرا | بیش از ۳ ماه | ۴ تا ۸ هفته | کمتر از ۴ هفته |

تفسیر:

- ۲۰ تا ۲۵: پایلوت را پیشنهاد بده.
- ۱۵ تا ۱۹: یک جلسه فنی/داده بگذار.
- ۱۰ تا ۱۴: nurture، فعلا قرارداد نه.
- زیر ۱۰: مودبانه خارج شو.

## پیشنهاد next step

«اگر موافقید، قدم بعدی این است که شما یک خروجی aggregate از یک کمپین قبلی بدهید. ما بدون داده خام کاربر، یک گزارش نمونه می‌سازیم: سگمنت‌ها، uplift، هزینه مشوق، تخمین هدررفت و policy پیشنهادی برای کمپین بعدی. بعد با هم تصمیم می‌گیریم آیا پایلوت ۴هفته‌ای ارزش دارد یا نه.»

## داده موردنیاز برای پایلوت

| ستون | توضیح |
| --- | --- |
| campaign_id | شناسه کمپین |
| segment | نام سگمنت |
| treatment | نوع مشوق یا کنترل |
| users | تعداد کاربران |
| conversions | تعداد خرید/فعال‌سازی |
| revenue | درآمد یا GMV |
| incentive_cost | هزینه مشوق |
| gross_margin | حاشیه سود تخمینی |
| start_date | شروع کمپین |
| end_date | پایان کمپین |

## شرط‌های رد پایلوت

- مشتری نمی‌تواند حتی داده aggregate بدهد.
- هیچ مالک مشخصی برای تغییر کمپین وجود ندارد.
- فقط دنبال گزارش نمایشی است، نه تصمیم عملی.
- انتظار دارد بدون کنترل‌گروه، نتیجه قطعی و causal بگیرد.
